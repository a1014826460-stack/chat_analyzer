# 下注结算日志与多线路当前期修复设计

## 目标

1. 每笔真实下注订单记录发送结果、站点、期号、群组、玩法和金额。
2. 开奖后按“用户 + 站点 + 期号”只生成一条结算日志，展示期开奖结果、投入、返还、净收益和盈亏结果。
3. 修复澳门、澳洲、挪威当前期响应结构漂移，使四条线路均能返回目标期和有效倒计时。
4. 让已脱敏的全局系统、第三方和异常事件对已认证用户可见，并避免运行日志只能看到登录和设置修改。

## 日志事件模型

订单日志保持逐笔粒度。`sent`、`failed`、`expired` 事件由 sender 在订单状态完成时写入，消息包含金额，结构化详情保留 `site`、`period`、`group_id`、`play_type`、`amount` 和 `status`。

结算日志采用每期汇总粒度。worker 在历史开奖写入后查找该用户该期所有 `sent` 订单，计算：

- `staked`：该期所有已发送订单金额之和；
- `payout`：命中订单金额乘玩法赔率后的总返还；
- `profit = payout - staked`；
- `outcome`：`profit > 0` 为盈利，否则为亏损。

使用 `StrategyEvent(event_type="settled")` 作为幂等标记。同一用户、站点、期号已有该事件时不重复写入运行日志。结算事件与运行日志在同一数据库事务提交。

结算消息格式固定为：

```text
结算：站点 PC28，期号 3465214，开奖结果 小双（和值 12），投入 100，返还 368，净收益 +268，盈利
```

## 全局运行事件可见性

`RuntimeLogEvent.user_id IS NULL` 表示所有已认证用户可见的脱敏服务事件，例如 worker 状态、第三方接口耗时和异常。日志查询返回“当前用户事件 + 全局事件”，仍不允许读取其他用户的事件。

worker 每个站点周期记录一条第三方抓取结果：成功为 `DEBUG/third_party`，失败为 `ERROR/exception`。URL 必须移除查询参数，异常堆栈经过现有脱敏器处理。UI 增加分类筛选，默认选择“下注与结算”，避免系统周期日志淹没业务日志；用户可切换到全部、系统、第三方或异常。

## 当前期适配

- 澳门：目标期使用最新 `qihao + 1`；若响应没有显式下期开奖时间，以最新 `opentime + 180 秒` 计算截止时间。
- 澳洲：目标期使用 `next.qi`；截止时间使用 `datetime.now() + next.sec`。
- 挪威：优先读取 `next_periods.PeriodNo/DrawTime`，回退到 `lottery_data[0].nextexpect/next`。
- PC28 保持当前 `countdown.next_draw_number/countdown_seconds` 逻辑。

所有站点响应必须通过固定 allowlist，未知站点返回 422，而不是内部异常 500。

## 验收标准

1. 一笔发送成功或失败的订单产生一条包含玩法和金额的日志。
2. 同一期 worker 连续运行多次只产生一条结算日志。
3. 结算仅统计 `sent` 订单；失败、过期和仅确认未发送订单不计入投入或收益。
4. 四站当前期适配器在固定响应样本中均返回非空期号和未来截止时间。
5. 已认证用户可查询自己的业务日志和全局服务日志，但无法读取其他用户日志。
6. UI 可按日志分类筛选，默认展示下注与结算，刷新、搜索和分页保持现有行为。
7. 重建 API 和 worker 后，四站现场探测不再出现澳门/澳洲倒计时为空或挪威 503。
